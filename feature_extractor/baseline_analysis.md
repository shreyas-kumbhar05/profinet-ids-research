# Baseline Analysis — What Does "Normal" PROFINET Traffic Look Like?

*This document forms the basis of Section 3 (Baseline Methodology)
of the research paper.*

## Dataset

- Source: 30-minute capture generated by `traffic_generator/generator.py`
- Configuration: 4 ms cycle time, 0.3 ms Gaussian jitter
- Captured PROFINET frames: 449,913
- Total feature rows: 449,912

The feature row count is one less than the number of captured frames
because the first frame has no previous timestamp from which an IAT can
be calculated.

---

## Feature 1 — Inter-Arrival Time (IAT)

| Statistic | Value |
|---|---:|
| Mean | 0.004000 s |
| Std dev | 0.004118 s |
| Min | 0.000002 s |
| Max | 0.726860 s |
| 1st percentile | 0.000254 s |
| 99th percentile | 0.016334 s |

**Observation:** The mean IAT is 0.004000 s (4.000 ms), matching the
theoretical 4 ms communication cycle almost exactly. The measured
standard deviation, however, is much higher than the configured
0.3 ms jitter. This is consistent with the timing behaviour observed
during Week 4, where sporadic operating-system and hypervisor scheduling
delays were observed while running inside VirtualBox.

The high maximum IAT indicates that a small number of isolated delays
occurred during the capture. These do not represent a change in the
average communication cycle, but they do increase the overall variance.

---

## Feature 2 — Frame Size

| Statistic | Value |
|---|---:|
| Unique values | 60 bytes (449,911 frames), 56 bytes (1 frame) |
| Constant size | No |

**Observation:** Almost all captured frames were 60 bytes, which matches
the expected size of the current generator output. One 56-byte frame was
observed at the end of the capture.

The short frame was inspected separately and had the expected PROFINET
EtherType, FrameID and sequential CycleCounter. Its exact cause was not
conclusively established, so the observation was retained rather than
being removed or normalized.

---

## Feature 3 — EtherType Distribution

| EtherType | Count | Percentage |
|---|---:|---:|
| 0x8892 | 449,913 | 100% |

**Observation:** All captured frames used EtherType `0x8892`, which is
expected because the tcpdump capture was explicitly filtered for
PROFINET RT traffic.

This 100% value describes the filtered experimental capture. An
unfiltered production capture would be expected to contain multiple
EtherTypes from different protocols.

---

## Feature 4 — Source MAC Consistency

| Statistic | Value |
|---|---:|
| Total feature rows | 449,912 |
| Known MAC frames | 449,912 |
| Consistency rate | 100% |

**Observation:** Every extracted frame matched the known source MAC used
by the baseline generator. This provides a stable normal value for the
MAC consistency feature.

A later spoofing experiment can introduce an unexpected source MAC and
use this feature as the corresponding anomaly signal.

---

## Feature 5 — Payload Entropy

| Statistic | Value |
|---|---:|
| Mean entropy | 0.0 bits/byte |
| Max possible | 8.0 bits/byte |

**Observation:** The simulated IO payload contains only zero bytes, so
the byte distribution produces approximately zero Shannon entropy.

This should not be interpreted as the expected entropy of all real
PROFINET payloads. It is a characteristic of the current simulation and
provides a clearly defined baseline for later payload-modification
experiments.

---

## Summary — Statistical Definition of "Normal"

Based on the 30-minute baseline capture, normal PROFINET RT traffic in
this simulation is characterized by:

1. Mean IAT of approximately 4 ms, with elevated variance caused by the
   VirtualBox execution environment.
2. Frame size of 60 bytes in almost all observations, with one isolated
   56-byte frame at the end of the capture.
3. A single observed EtherType, `0x8892`, because the capture was filtered
   to PROFINET RT traffic.
4. 100% source MAC consistency.
5. Near-zero payload entropy because the simulated IO payload is filled
   with zero bytes.

These observations define the baseline against which controlled
anomalous traffic will be compared.

---

## How This Drives Week 6 Attack Design

Each planned attack changes one or more characteristics of the normal
baseline.

| Attack | Feature(s) Violated | Expected Deviation |
|---|---|---|
| Replay | IAT / CycleCounter | Repeated frames and abnormal timing/sequence behaviour |
| Spoof | `src_mac_known` | Changes from `True` to `False` |
| Malformed | `frame_size`, `payload_entropy` | Unexpected frame size and increased payload entropy |

The purpose of this approach is to make each attack a controlled
deviation from a known baseline rather than simply generating arbitrary
abnormal packets.

---

## Limitations

The IAT statistics are affected by the execution environment. Although
the mean remains close to the intended 4 ms cycle time, the measured
standard deviation is substantially higher than the configured 0.3 ms
because of sporadic scheduling delays observed while running the
generator inside VirtualBox.

The payload entropy baseline is also specific to the current simulation,
where the IO payload is filled with zero bytes. Real PROFINET devices may
produce structured payloads with different entropy characteristics.

The single 56-byte frame found at the end of the capture was retained in
the analysis because its exact cause could not be conclusively
established.
